# v0.2.0 engineering semantics

Prepared 5 September 2026. Engine version 0.2.0; existing project schema version 1 remains compatible. No new commercial-format or manufacturing qualification is implied.

## Exact search means a defined finite scope

`optimizeExact` selects an allowed forward stage. Sources must have an effective net, must not be reserved/NC or locked, and must not have outgoing connections to another stage. A source attached to a fixed/locked target is fixed. Targets occupied by outside-scope sources remain unavailable. Other stages and coordinates are unchanged. A `sourceIds` subset defines a small engineering-change window; it does not silently select or shrink a problem.

At most 12 sources and 64 candidate targets are admitted before the cost matrix is built. This is a deliberate safety limit, not a capacity or latency guarantee. An oversized scope raises an input/resource error, not an infeasibility result. The original larger-stage heuristic remains available separately.

The objective is full-project physical Manhattan length + configured crossing weight × same-stage straight-ratsnest crossings + `changePenalty` × changed source targets. `maxChanges` limits remapping churn. Defaults are 50,000 search nodes and 5 seconds; allowed maxima are one million nodes and 60 seconds. Input analysis is also bounded. Timing limits are checked between search nodes, not hard real-time interruption of an individual analysis.

The branch-and-bound lower bound uses the remaining rectangular linear assignment optimum plus fixed/assigned length. Nonnegative crossing penalties are omitted from that bound. Complete candidates are independently evaluated by the ordinary full rule engine; incomplete/truncated analysis cannot be accepted. Effective signals on locked sites are preserved. Search never mutates its input.

| Status | Meaning |
|---|---|
| `optimal` | Exhaustive completion/pruning in this finite stage-local floating-point model, with a checked feasible incumbent. |
| `feasible` | A checked incumbent exists, but a node/time/analysis budget stopped the search. Reported gap is an absolute objective gap to the conservative bound, not a percentage. |
| `unknown` | Search stopped without a checked incumbent. No infeasibility proof. |
| `infeasible` | Exhaustive search found no complete passing mapping in the stated scope, or a necessary-condition Hall deficiency rules it out. Other stages/coordinates/rules could make a different problem feasible. |
| `unchecked` | Initial rule analysis was incomplete. |
| `no-op` | No movable sources. Feasibility still reflects existing rule findings. |

A Hall witness names a subset of sources with fewer necessary-compatible targets than sources. It does not explain every kind of coupled infeasibility. It is not an unsatisfiable-core service for arbitrary EDA rules.

The optimizer uses JavaScript floating-point arithmetic and conservative pruning slack. Results are **not exact-rational formal proofs**, global full-chip optima, routing optima, or physical signoff certificates. Comparing the independently enumerated small problems in the tests is the current correctness evidence.

## Conservative routing model

`routeStage` uses a four-neighbor XY grid and adjacent routing-layer moves. Horizontal/vertical cost is grid pitch; each layer transition costs `viaCost`. Different deterministic route orders can be tried, but the multi-net method remains heuristic. It is not a complete global router or negotiated-congestion algorithm.

Options include pitch, layer count, planar clearance, origin, dimensions, start/end layers, via cost, expansion/time budgets, and route-order trials. Endpoints must lie on the declared grid: changing pitch to make a terminal off-grid yields `OFF_GRID`, not silent snapping. Default padding helps avoid artificial edge congestion; explicit origins/dimensions are supported for reproducibility.

Limits: up to 512 selected assignments, 1–8 layers, 262,144 total grid cells, two million maximum expansions, and at most one million witness nodes checked. Rectangle obstacles are conservatively inflated by clearance plus half a grid pitch and transformed with their die. Terminal/reserved columns and inter-route square clearance neighborhoods are blocked conservatively. Grid conservatism may reject a physically possible route. User clearance is a model input, not a foundry-derived physical rule.

`verifyRoutes` is independent of the A* search: it checks the witness rather than trusting the router's pass flag. It shares canonical project, grid, and obstacle definitions with the router; it is **not an independently developed second EDA implementation**. It verifies current design content, exactly the expected assignment IDs, endpoint coordinates/layers, unit grid steps, no loops, obstacles, collision/clearance, full route coverage, recomputed planar length/vias, configured length limits, and differential-pair planar length mismatch. It refuses stale designs even when the old geometry would happen to remain routable.

A `routed` result requires all selected routes and a passing witness check. `partial`, `constraint-failed`, and `input-invalid` are not successful routes; failure is not proof that the physical problem is unroutable. A single-stage witness does not certify the entire stack. Off-stage geometry, real trace widths, via barrels/pads, impedance, return paths, layer thickness, plating, die-face orientation, skew from dielectric/via delay, and manufacturing DRC are not modeled.

Route JSON preserves every grid node and model input. SVG is a visualization, not an electrical/netlist or manufacturing interchange format. Planar wire length excludes physical Z/via length, which is not defined in this model. Via count is reported separately. The old ratsnest crossing metric intentionally remains separate from verified routing-layer occupancy.

## Review integrity, authenticity, and freshness

A review payload contains exactly project, validation, optional routing, and optional routing-verification members. SHA-256 binds each member to a canonical manifest including engine version, pass states, warning count, and scope. Object key order is normalized; array order is preserved. Project hashes include normalized revision/audit metadata. Routing staleness instead compares full canonical engineering content while excluding revision/audit labels.

Verification recomputes every member digest and reruns planning/witness checks. Supplying `--project current.json` pins the expected project digest and rejects a valid-but-old review. A bare hash check verifies self-consistency, not that the reviewed design is the intended latest revision. Engine-version mismatch is rejected rather than silently reusing old rule semantics.

Hash-only bundles can be replaced and rehashed by an adversary. For authenticity, `sign-bundle` uses Node's Ed25519 implementation to sign the canonical manifest. `verify-bundle --public-key` requires an externally trusted key; an untrusted embedded key is not accepted as authority. Key fingerprints are SHA-256 of the base64-encoded DER SPKI public key. Private keys are never embedded in the bundle or application.

The signer rejects invalid bundles and projects with hard-rule failures; warnings remain explicit and are not automatically approval blockers. A signature proves possession of a trusted key and binds the manifest—it does not establish a person's role, approval authority, revocation status, trusted timestamp, or foundry acceptance. There is no multi-user authorization, key management service, revocation list, or append-only remote transparency log.

Native WebCrypto SHA-256 is preferred. A bounded pure-JavaScript SHA-256 fallback supports offline managed contexts lacking WebCrypto and is cross-tested against Node/OpenSSL. It provides hashing only; signature creation/verification stays in the Node CLI's native crypto implementation. This is not a cryptographic certification or external security audit.

## User interaction safety

Search and routing run in cancellable workers. Completed results are tied to full canonical content, not the short FNV review label. Changed designs reject in-flight results and mark stored results stale. Exact Apply is explicit and goes through the normal full-rule transaction; undo/redo remain available. A partial or stale route cannot be bundled as a passing route review.

Local storage remains convenience persistence. Export JSON to retain work. Native origin persistence and cross-browser operation were not verified in the managed local browser session; use the optional native browser suite on a normal workstation/CI runner.
